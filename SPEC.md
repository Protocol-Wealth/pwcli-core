# pwcli-core Specification

`pwcli-core` defines a deterministic architecture for AI-native applications
that use a conversational or CLI-like surface as an intent compiler while
keeping application state, permissions, and user interface primitives under
traditional software control.

## 1. Architecture Model

The system has two engines:

- **Dynamic overlay:** Natural-language input, intent classification, candidate
  panel selection, clarification, and summaries.
- **Static bedrock:** Routes, schemas, databases, registered panels, typed
  tools, approvals, audit logs, source records, and fallback views.

The dynamic overlay never replaces the static bedrock. It only selects from
registered capabilities and compiles fuzzy human input into structured payloads.
Existing agent runtimes can sit underneath the bedrock, but they should enter
through explicit adapter metadata that declares side effects, data access,
redaction, approval, and audit requirements.

## 2. Trust Boundary

AI may:

- classify human intent;
- select registered panels and routes;
- propose actions;
- parse, summarize, and map data;
- ask clarifying questions;
- draft artifacts.

AI may not:

- invent new routes at runtime;
- alter database schemas;
- execute unvetted writes;
- mutate user permissions;
- bypass approval gates;
- treat untrusted source text as instructions;
- generate live UI code for execution.

## 3. Core State Machine

```text
State A: Console
  Human input is accepted as lossy text, voice, or gesture.

State B: Intent Telemetry
  The system compiles input into intent.schema.json.

State C: Hydrated Panel
  A registered primitive receives deterministic backend data.

State D: Approval Gate
  Required for state-changing or permission-sensitive actions.

State E: Return Focus
  The panel collapses into the command stream with a concise artifact.

State F: Static Fallback
  Low confidence or explicit user request opens a deterministic route.
```

## 4. Standards Before Invention

Before introducing a custom data contract, `pwcli-core` implementations should
ask whether an existing open standard already covers the layer:

- APIs: OpenAPI, JSON Schema.
- Agent tools and data: MCP.
- Agent delegation: A2A.
- Web and public docs: llms.txt, sitemap.xml, schema.org, JSON-LD.
- Archives: OAI-PMH, Dublin Core, MARC 21, IIIF.
- Datasets: DCAT, RO-Crate.
- Rights, licensing, and BOM metadata: SPDX.
- Provenance: W3C PROV-O.

Custom schemas are acceptable when no standard fits, but the custom schema must
preserve source identifiers, provenance, rights, confidence, human review state,
fallback routes, and raw source references.

## 5. Assertions

Implementations must separate:

- **Descriptive source metadata:** what a repository, API, file, or record
  explicitly claims.
- **Interpretive AI output:** summaries, classifications, inferred entities,
  risk notes, and recommendations generated by a model.

Interpretive output may cite source metadata, but it must not overwrite it.

## 6. Elastic Primitives

Elastic primitives are registered UI components that can be selected by intent.
They are not generated by the model at runtime. Each primitive should declare:

- identifier;
- supported intents;
- data contract;
- fallback route;
- side-effect level;
- approval requirement;
- source/provenance requirements;
- supported input and output modes;
- optional preview, cost, risk, empty/loading/error, primary action, and undo metadata.

See [schemas/primitive.schema.json](schemas/primitive.schema.json) and [docs/human-ux-guide.md](docs/human-ux-guide.md).

## 7. Runtime Adapters and Redaction

`pwcli-core` can wrap existing agent infrastructure without importing or
reimplementing it. Runtime adapters describe how external systems such as
OpenAI Agents SDK, LangGraph, MCP servers, A2A agents, Goose, Claude Code, the
Claude Agent SDK, or
custom runtimes fit into the control plane.

Runtime adapters must declare:

- execution mode;
- data access;
- allowed data classes;
- side-effect level;
- redaction requirement;
- approval and audit requirement;
- integration boundary.

Redaction policies must declare the sensitive data classes, redaction stages,
actions, default handling, human-review requirement, audit requirement, and
retention expectation. Runtime adapters must also declare untrusted input
handling so poisoned issues, comments, documents, tool outputs, or external
agent results do not become trusted instructions. Run receipts must minimize
content: record policy identifiers, timestamps, event counts, redaction counts,
and result digests rather than prompts, outputs, tool arguments, credentials, or
transcripts. See [schemas/runtime-adapter.schema.json](schemas/runtime-adapter.schema.json),
[schemas/redaction-policy.schema.json](schemas/redaction-policy.schema.json),
[schemas/run-receipt.schema.json](schemas/run-receipt.schema.json),
[docs/agent-runtime-adapters.md](docs/agent-runtime-adapters.md),
[docs/privacy-redaction-control-plane.md](docs/privacy-redaction-control-plane.md),
[docs/agent-poisoning-defense.md](docs/agent-poisoning-defense.md), and the
[Claude Agent SDK reference adapters](examples/claude-agent-sdk-adapters/README.md).

## 8. Context Packs

A `context-pack/` directory stores small, reviewed Markdown files with YAML
frontmatter. These files provide stable operating context for agents and humans.

Context packs are not a substitute for source data, databases, policy, or
authorization. They are version-controlled context references.

## 9. Output Hierarchy

When designing a feature, implementations should document work in this order:

1. Source schema and standards crosswalk.
2. Deterministic bedrock configuration.
3. Primitive registration.
4. Intent orchestration logic.
5. Typed sandboxed execution layer.

This keeps AI-native interfaces grounded in inspectable infrastructure.
